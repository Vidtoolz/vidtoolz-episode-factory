# ELIGIBILITY.md — permission declaration vs authorization eligibility (v1.7, FROZEN_NOW as law; evaluator is a reference, not runtime-qualified)

**Permission declaration** (`PERMISSIONS.json`, `allowed: true`): what an operation is theoretically permitted to do under a milestone and scope. **Authorization eligibility**: whether *this* request, the frozen authorities, the **active reviewed authority** and the linked evidence set currently satisfy every prerequisite. `allowed: true` never makes a request eligible.

## v1.6 law: the evaluator consumes validated, envelope-bound, current evidence and the ACTIVE MATRIX CONTENT — never caller assertions

AUTHORIZING evaluator: `authority_lib.evaluate_eligibility_authorizing(perms, request, read_primitives, capabilities, target_contract, GovernedEvidenceSet, active)` — or `evaluate_eligibility_for_session(session_id, ...)`, which loads through `load_governed_evidence_set` itself. It takes no attachment-state parameter and recomputes the state from the governed document, and it is fail-closed: absent or invalid location provenance yields `eligible: false` with reason code `LOCATION_AUTHORITY_INVALID`.

`authority_lib.evaluate_eligibility(perms, request, read_primitives, capabilities, target_contract, evidence_set, active)` is the same semantic evaluation over a bare evidence set and is **DIAGNOSTIC / NON_AUTHORIZING** (v1.14, V113-B1). It is for fixtures, in-memory evidence sets and diagnosis, and must never be selected for an authority decision. The transaction and commit paths follow the same split: `commit_eligibility_authorizing` → `validate_transaction_set_authorizing` over a `GovernedEvidenceSet` is the ONE authorizing commit path (v1.15, V114-B2), and the bare-dict `commit_eligibility` / `validate_transaction_set` pair is `PROVISIONAL_UNTIL_M3` and non-authorizing. Everything below describes the shared semantics of both.

`active` = `{authority_version, manifest_sha256, capability_matrix_sha256}` of the reviewed authority the evaluator runs under (this bundle: `1.7.0`, the sha256 of its `FREEZE-MANIFEST.json`, and the **canonical content digest** of its `CAPABILITIES.json` object under domain `vidtoolz.resolveCapabilityMatrix.v1`). It is an input of the deployment, not of the request. Every evidence record must be envelope-bound to it (`TARGET-ATTACHMENT-GATE.md`); a set containing a record bound to another manifest or authority version is invalid and the derived state is `CONFLICT`.

**The supplied capability matrix must BE the active matrix.** Before anything else, the shared evaluation body (`evaluate_eligibility_authorizing` on the authorizing path, the diagnostic `evaluate_eligibility` on the non-authorizing one) calls `active_authority_errors(capabilities, active)`: if `digest(capabilities, vidtoolz.resolveCapabilityMatrix.v1) != active.capability_matrix_sha256`, the result is `CAPABILITY_MATRIX_NOT_ACTIVE` and nothing is eligible. An invented matrix — schema-valid, with plausible promotion metadata, even citing the digest of the real zero-qualified matrix — cannot qualify a primitive (`REVIEW-REFREEZE.md` §3).

Inputs are the frozen authorities (`PERMISSIONS.json`, `READ-PRIMITIVES.json`, `CAPABILITIES.json`, `TARGET-CONTRACT.json`), the active authority, a **validated evidence set** (`schemas/resolveEvidenceSet.schema.json`: `current_session_id`, `evaluated_at`, content-addressed envelope-bound records) and a **request** (`schemas/resolveEligibilityRequest.schema.json`): `milestone`, `operation`, `scope`, `expected_project_name?`, `expected_timeline_name?`, `transaction_id?`, `plan_digest?`, `plan_h0_guard_digest?`, `refs` (sha256 references by role: `authorization`, `journal_prepared`, `read_only_journal`, `guard`, `plan_validation`, `m0_exit`, `m1_exit`, `m2_exit`, `exclusive_session`, `media_class`, `destination_timeline`).

The request schema has `additionalProperties: false`: `attachment_state`, `capability_state`, `evidence`, `journal_available`, `guard_available`, `authorization_token` are **not request fields** (retired). The evaluator never reads them; fixtures `m0-probe-deny-declared-state-ignored` and `m0-connect-deny-qualified-read-string-ignored` prove a request carrying them is both schema-invalid and still denied.

Derived, not declared:
- **Attachment state** — `derive_attachment_state_authorizing(target_contract, GovernedEvidenceSet, active)` on the authorizing path, or the DIAGNOSTIC `derive_attachment_state(target_contract, evidence_set, active)` on the non-authorizing one (`TARGET-ATTACHMENT-GATE.md`). `TARGET_STATE_*` codes compare the derived state; `CONFLICT` short-circuits the whole evaluation with reason `ATTACHMENT_CONFLICT` and the conflict list; nothing is eligible.
- **Primitive qualification** — `primitive_status(capabilities, read_primitives, method, evidence_set, env, active, rp=read_primitives)` → `capability_qualification`: `QUALIFIED_CALLABLE` only when, all recomputed at call time, (1) the supplied matrix IS the active matrix by content digest; (2) the row is `QUALIFIED_READ` under a reviewed `refreeze` block bound to the active `parser_version`/`parser_sha256` and `primitive_spec_sha256`; (3) the row's evidence entry names `(method, receiver_class, probe_id, raw_capture_sha256, derived_result_sha256, review_decision_sha256, parser, spec, version_match, reviewed_refreeze_version = this matrix version)` and the refreeze block **and** a `REFREEZE_RECORD` in the evidence set promote exactly those digests under the same probe and session; (4) the `RAW_CAPABILITY_CAPTURE` resolves, is structurally a facts-only capture, re-hashes and is bound to the active authority and the contract environment; (5) the reference parser derives `SUCCESS` **now** and its digest equals the promoted `derived_result_sha256` (a stored `DERIVED_CAPABILITY_RESULT` must equal the recomputation); (6) the `REVIEW_DECISION` is a valid `ACCEPT` of exactly that raw+derived pair by a reviewer who is not the capture operator. `PROBE_ALLOWED` only inside `READ_PRIMITIVE_QUALIFICATION_PROBE` for `probe_candidate` rows. Otherwise `UNQUALIFIED` and the declared fallback decides (`REFUSE` blocks). No label, review, refreeze or matrix substitution can override a derived failure (`REFERENCE-PARSER.md`, `REVIEW-REFREEZE.md`).
- **Evidence references** — `resolve_ref(evidence_set, ref, expected_type, envelope, extra, active)`: a reference is evidence only if it is a lowercase 64-hex sha256, exists in the set, has the expected `record_type`, re-hashes to its id, is bound to the active manifest and authority version, and matches the required envelope fields (host; for session-scoped roles the current `session_id`; for project/timeline-scoped roles the expected names) and extra fields (`plan_digest`, `transaction_id`, `milestone`, `authority_version`, `scope`, `library_name`, `result`). `""`, `"false"`, uppercase, short, unlinked, wrong-type, other-manifest or other-host references fail (fixtures `m0-deny-ref-*`, validator `evidence-ref-negative`). `GUARD_CURRENT` additionally requires the referenced `GUARD_SNAPSHOT` to be the **current** guard observation of the session for that project/timeline (a newer guard record makes the plan stale: fixture `plan-guard-record-not-current`) **and, for a mutation-capable or guard-requiring operation, to pass the H0/S0 early write gate below**.
- **Target requirement** — every permission entry and logical read operation declares `target_requirement ∈ {SESSION, PROJECT, PROJECT_TIMELINE}` (must agree; `semantic_read_primitives`). `SESSION`: host/session/library boundary only (`READ_PRIMITIVE_QUALIFICATION_PROBE`, `CONNECT`, `ENUMERATE_PROJECTS`, `CreateProject`); no project or timeline record is required or consulted (fixture `m0-enumerate-projects-allow-without-any-binding-records`). `PROJECT`: `expected_project_name` proven by the **current** `PROJECT_BINDING_OBSERVATION` of the current session for that name, whose envelope cites the contract library and the provisioning record; the name must be adapter-prefixed or covered by an `OPERATOR_PROVISIONED_PROJECT` record for the contract library (`ENUMERATE_TIMELINES`, `TRIPWIRE_READ`, `LoadProject_adapterPrefixed`, `CreateEmptyTimeline`, `SaveProject`, `ImportMedia`). `PROJECT_TIMELINE`: additionally `expected_timeline_name` proven by the current `TIMELINE_BINDING_OBSERVATION` bound to the same library, provisioning record, project (name and id) and timeline (`SNAPSHOT_CAPTURE`, `TIMEBASE_OBSERVE`, `SetCurrentTimeline`, `BUILD_MUTATION_PLAN_DRY_RUN`, every M3 timeline mutation). Mutation-capable entries additionally require `OBSERVED` project/timeline unique ids. Bindings from another session, another library or another provisioning record never bind (fixtures `m0-snapshot-deny-binding-from-other-session`, `m0-snapshot-deny-cross-library-timeline-binding`). **No operation ever binds to whatever project or timeline is current.** The evaluator enforces the binding even if an entry omitted `TARGET_REQUIREMENT_SATISFIED`.

## v1.6 H0/S0 early write gate (evaluated BEFORE any mutator, never deferred to the composed path)

`GUARD_CURRENT` on an operation whose entry is `mutation_allowed` or which is in `GUARD_REQUIRED_OPS` resolves the referenced `GUARD_SNAPSHOT` record and runs `guard_record_errors` (`GUARD-AUTHORITY.md`), which recomputes the guard digest and the provenance digest from the record's own guard object and provenance map and then requires:

| Code | Requirement |
|---|---|
| — | the plan's `h0_guard_digest` is this guard record |
| `H0_PROFILE` | `coverage.profile` satisfies `WRITE_PRECHECK` (`profile_satisfies`); a `MINIMAL_M0` or `FULL_TIMELINE_READ` snapshot never can |
| `H0_INCOMPLETE` | `coverage.complete` is true |
| `H0_DOMAINS` | every mandatory domain of the required profile is observed |
| `H0_IDENTITY` | project and timeline `unique_id_status` are `OBSERVED` |
| `H0_PROVENANCE` | every provenance entry is `QUALIFIED_OBSERVATION` resolving to the capture the active matrix promotes for that method, and the producing primitives of every mandatory field carry that provenance |
| `H0_MATRIX` | the guarded snapshot's `policy.capability_matrix_sha256` and capabilities version are the active ones |
| `H0_AUTHORITY` | the guard record's authority version is the active one |
| `H0_TARGET` | the guarded library/project/timeline/epoch identity equals the plan target (`request.plan_target`) |

`PLAN_VALIDATION` records are valid only when produced by the composed validator (`validator = tools/authority_lib.py#validate_transaction_set_authorizing`, or the PROVISIONAL_UNTIL_M3 non-authorizing `#validate_transaction_set` for diagnosis, `stages_completed ⊇ {s0, plan}`) and when they name this plan's H0 guard; a record produced by a per-document helper, or naming another H0, is refused. "Rejected later by composed validation" is not a pre-write gate: this evaluation happens before a mutator could run (Codex F15-03, Claude M-H0).

Output: `permitted_by_policy`, `prerequisites_satisfied`, `eligible`, `failed_prerequisites[]` (code + reason), `reason_codes[]`, `derived_attachment_state`, `attachment_conflicts[]`, `target_requirement`, `expanded_primitives[]` (method, status, callable, fallback). Unknown milestone/scope/operation/prerequisite, invalid or unbound evidence set, `CONFLICT`, missing binding or unlinked reference fails closed. The result is a pure function of its inputs: the validator re-evaluates every case under seeded permutations of the evidence map and request key order and requires identical output.

## Consequences at v1.6

`CAPABILITIES.json` has zero `QUALIFIED_READ` rows and an unreviewed `refreeze` block, so `callable_method_set` is empty: `CONNECT` and `TIMEBASE_OBSERVE` (`REFUSE` fallbacks) are not eligible at any milestone; `READ_PRIMITIVE_QUALIFICATION_PROBE` is the first and only session-establishing M0 operation; `ENUMERATE_PROJECTS`, `ENUMERATE_TIMELINES`, `TRIPWIRE_READ` and `SNAPSHOT_CAPTURE` are eligible only in degraded mode once the derived state is `ATTACHED_READ_ONLY` and their bindings are current — and a degraded `SNAPSHOT_CAPTURE` may contain only what `SNAPSHOT-COMPLETENESS.md §Pre-qualification capture` allows. Qualification happens only through the pipeline in `M0-PROBE-CONTRACT.md`.

Fixtures: `fixtures/eligibility/cases.json` (cases listed in `VALIDATION-REPORT.md`; each names its evidence set under `fixtures/evidence/`, the capabilities file, expected eligibility, expected failing code, expected derived state and request-schema validity). `fixtures/eligibility/capabilities-hypothetical-refreeze.json` is HYPOTHETICAL_NOT_AUTHORITY and exists only to prove the positive callable path, every raw-capture rejection and the H0 early write gate. Cases marked `forge_matrix` replace the matrix content while keeping the active digest and must be refused with `CAPABILITY_MATRIX_NOT_ACTIVE`.
